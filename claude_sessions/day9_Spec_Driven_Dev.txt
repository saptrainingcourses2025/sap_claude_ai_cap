     Travel Management CAP App — CatalogService + UserManagement

     Context

     .claude/specs/tyson_spec_srv.md defines two OData services (CatalogService,
     UserManagement) that don't exist yet — srv/ is currently empty.
     db/schema.cds and db/common.cds already exist but model a different,
     earlier domain (traveller addresses via Destinations, Contacts, Vacations,
     a flat AppUsers with a single role), which conflicts with the spec's entity
     shapes in most places (no TravellerTypes, no TravelledLocations,
     Destinations means something else, no Roles/UserRoles many-to-many,
     Travellers is missing email/phone/typeCode/userID).

     Per user decision, we are rebuilding db/ to match the spec exactly,
     deleting Vacations/Contacts (not spec-covered), and regenerating all CSV
     seed data to fit the new shapes while reusing existing sample names/places
     conceptually. This plan implements the full db + srv layer plus supporting
     config, seed data, i18n, and tests.

     Two design ambiguities in the spec are resolved as follows (flagged since
     they're judgment calls, not literal spec text):
     - Roles/UserRoles shape: the spec's own $expand example
       (Users?$expand=roles($select=role_ID;$expand=role(...))) implies
       UserRoles is UUID-keyed, not code-keyed — so
       UserManagement.Roles/UserRoles are new cuid entities in db/schema.cds,
       distinct from (and replacing) the old db/common.cds Roles CodeList.
     - Destinations 405 on PATCH/DELETE: @readonly would also block CREATE
       (contradicts the spec's required POST → 201), so use @insertonly instead,
       which permits CREATE+READ and blocks UPDATE/DELETE.
     - Traveller-role CREATE on Travellers/TravelledLocations: @restrict's where
       clause can't scope an INSERT (no row exists yet), so CREATE is granted
       to Traveller in CDS, and a before('CREATE') handler force-sets
       userID/validates ownership server-side.

     db/common.cds (rewrite)

     Keep AddressTypes, TravellerStatus as read-only CodeList entities; add a
     new TravellerTypes CodeList (codes FF/EX/ST — Frequent
     Flyer/Executive/Standard). All three get @readonly @cds.autoexpose. Remove
     the old Roles CodeList and Role type entirely (replaced by the new
     UUID-keyed Roles/UserRoles in schema.cds — see above). Add types
     AddressType, Status, TravellerType as associations to the three code lists.

     db/schema.cds (rewrite)

     - Destinations (@insertonly, immutable master list): ID (cuid), name
       (String(200), mandatory, @assert.unique), country/city (String(100),
       mandatory), region (String(100), optional), description (LargeString,
       optional).
     - Travellers (cuid): firstName/lastName (String(80), mandatory), fullName
       (virtual, @Core.Computed, never persisted), email (String(120),
       mandatory, @assert.unique), phone (String(20), optional), addressType
       (assoc to AddressTypes), type (assoc to TravellerTypes, mandatory),
       status (assoc to TravellerStatus, mandatory, default 'A'), userID
       (String(100), mandatory — row-filter key), locations (Composition of many
       TravelledLocations on locations.traveller = $self — named locations
       specifically because spec Section 9's $expand=locations(...) examples
       require that property name), modifiedAt (Timestamp, @cds.on.update: $now,
       @odata.etag).
     - TravelledLocations (cuid, immutable log — no Update): traveller (assoc to
       Travellers, mandatory), destination (assoc to Destinations, mandatory),
       travelFrom/travelTo (Date, mandatory), notes (LargeString, optional).
     - Users (cuid): loginName (String(120), mandatory, @assert.unique),
       firstName/lastName (String(80), mandatory), isLocked (Boolean, default
       false), createdAt (Timestamp, @cds.on.insert: $now), roles (Composition
       of many UserRoles on roles.user = $self).
     - Roles (cuid, new — see ambiguity note above): code (String(10),
       mandatory, unique), name (String(80), mandatory), descr (String(255)).
     - UserRoles (cuid, junction): user (assoc to Users, mandatory), role (assoc
       to Roles, mandatory).

     No managed aspect anywhere — spec's field tables are deliberately minimal
     (no createdBy audit trail beyond what's explicitly listed).

       { grant: '*', to: 'Admin' }
     ];
     annotate CatalogService.TravelledLocations with @restrict: [
       { grant: ['READ','CREATE','DELETE'], to: 'Traveller', where:
     'traveller.userID = $user' },
       { grant: '*', to: 'Admin' }
     ];
     annotate CatalogService.Destinations with @restrict: [
       { grant: ['READ','CREATE'], to: 'authenticated-user' }
     ];
     (Value-help entities get simple READ-only @restrict to authenticated-user.)

     srv/user-management.cds
